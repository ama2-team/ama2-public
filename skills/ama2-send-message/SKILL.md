# Send a message in AMA2

Use this skill to deliver a message to an existing AMA2 thread.

## When to use

- "Send 'sounds good' to the design thread."
- "Reply to my latest unread message saying I'm in a meeting."
- "Tell @alice that the build is green."

If the user names a person or agent but no thread exists yet, use `ama2-create-thread` first, then come back here.

## How to do it

1. Resolve the target thread.
   - If the user gave a thread title or name, call `ama_threads_list` and match by title.
   - If the user said "the latest" or "my unread", call `ama_threads_pending` and pick the top result.
   - If the user gave a thread ID, use it directly.
   - Confirm the chosen thread with the user before sending if there is any ambiguity.
2. Compose the message text. Keep it as the user phrased it — do not rewrite tone unless asked.
3. Call `ama_thread_send` with `thread_id` and `message_text` (these are the exact field names accepted by the tool). Optionally pass `mentions` (an array of agent sender IDs) when the user explicitly asks to ping someone.
4. Report the resulting message ID and a one-line confirmation back to the user.

## Things to watch

- The MCP tool only accepts these inputs: `thread_id`, `message_text`, optional `client_message_id`, optional `mentions`. Any other field is rejected (the schema is strict). In particular, do not pass `body`, `text`, or `content`.
- `client_message_id` is auto-generated by the MCP server when missing, null, or blank; do not invent one. Supply your own only when you need a stable client-side reconciliation id for a known logical message. Transport retry deduplication uses the separate `Idempotency-Key` header.
- If the send fails with an authentication error, suggest the user run the CLI auth flow (`ama2 auth login`) or check their `AMA2_PROFILE` env var.
- Never send a draft without showing it to the user first when the user only described the _intent_ ("tell them I'll be late") rather than the exact text.
